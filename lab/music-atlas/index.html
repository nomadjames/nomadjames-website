Music Atlas

A 51,302-track archive is useless if the only way back in is remembering what to search for. Music Atlas starts with one record, then follows tempo, key, artists, collaborators, versions, labels, release context, and unresolved acquisition leads.

Loading the sanitized corpus…

01 / THE IDEA

The library remembers files. I wanted it to remember relationships.

DJ software is good at storing records and weak at helping a person recover the connections between them. I wanted to choose one track I already knew, then ask what else in the archive could sit near it by pace, harmonic position, credit, release lineage, or scene context. The result is a retrieval tool for forgotten repertoire.

Search by artist or title, choose one analysis source, set the tempo tolerance and key rule, then inspect the connection map or follow any archived result as a new seed. Every match says why it appeared. There is no hidden taste model and no visitor-triggered provider API.

02 / THE FRICTION

The software disagrees about pitch.

Exact normalized-key agreement between Serato and Rekordbox across active repertoire.

90.23%

Tempo can be normalized conservatively. Key cannot. The interface keeps Serato, Rekordbox, and Traktor separate and makes the visitor choose which analysis lane controls the match.

03 / PUBLIC BOUNDARY

Real corpus. Deliberately narrow export.

The private archive contains 51,302 audio tracks. The public instrument ships a reviewed cohort from the 5,873-track active repertoire, one explicit Myd seed, and sanitized unresolved Rekordbox leads.

Public music metadata is limited to artist, title, album, genre, year, label, source-specific BPM and key, and allowlisted music links. No audio, paths, filenames, play counts, activity dates, crates, comments, ISRCs, arbitrary URLs, or private library identifiers are public. The browser receives a static reviewed snapshot and never connects to the source catalog or a provider API.

04 / THE 100-TRACK BAKEOFF

One hundred tracks, sixteen model lanes, one eight-gigabyte card.

I tested what actually finds a useful neighboring record, what merely fits on the hardware, and what cannot legally ship with the product.

I ran sixteen local audio-analysis lanes across one hundred anonymous tracks on an NVIDIA RTX 2080 SUPER with eight gigabytes of VRAM. Every lane finished. The complete sequential run took twenty-three minutes and six seconds, including the models that had to stay on CPU.

That is the clean result. The useful result is messier.

Music Atlas needs several kinds of truth at once. Tempo and musical key should be repeatable and attributable. Artist, label, version, and release relationships should remain explicit metadata. Learned models should find acoustic, stylistic, and semantic neighbors that those fields cannot describe. Asking one embedding to absorb all of that would make the interface simpler and the evidence worse.

The test was built to find that boundary.

THE HUNDRED-TRACK GATE

A fixed sample before a fifty-one-thousand-track commitment.

The sample contained one hundred unique thirty-second MP3 excerpts, divided evenly across ten broad source categories. Every artist, album, label, and release appeared once. That removed obvious identity shortcuts, but it also removed several useful validation routes. A model could not score points by finding another track from the same artist because no such track existed.

The remaining category label was weak ground truth. It came from broad source organization, not a controlled listening study. Random category precision at five was 0.091. In plain language, a random model would place fewer than one-half of one same-category track among the five nearest neighbors on average.

Folder labels can test broad organization.They cannot decide whether an unexpected neighbor is musically useful.

The source clips stayed read-only. The runner checked each SHA-256 hash before inference, loaded one model once, processed all one hundred clips, wrote an atomic checkpoint after every track, then exited before the next model took the card. No audio or embeddings left the workstation.

The final receipt verified one hundred unchanged source hashes, sixteen completed lanes, zero model failures, seventy-one hashed model artifacts, and no partial checkpoints. All fifteen embedding lanes produced finite, dimension-correct, normalized vectors. TempoCNN supplied the sixteenth lane.

The protocol survived contact with the machine.

WHAT WON THIS TEST

The smaller task-specific models beat the fashionable foundation models.

Category precision at five is the share of a track's five nearest neighbors that came from the same broad source category. Discogs EffNet through ONNX led at 0.304, more than three times the random baseline, with mean average precision of 0.283. It processed a track in 0.38 seconds at the median.

The artist-trained Discogs embedding followed at 0.282. MusiCNN reached 0.274. Discogs models occupied six of the first eight positions, with MAEST and MusiCNN interrupting the run.

Discogs won this category test. It did not win every job Music Atlas has.

CLAP landed barely above the random category baseline, but this experiment never asked it to retrieve audio from text. That is its distinct value. A query such as “dark broken techno with soft pads” needs a shared text-audio space, not another folder classifier. CLAP remains the permissively licensed candidate for that lane.

OMAR-RQ also needs a narrower interpretation. I averaged layer-six features into one vector without learning a pooling function or fine-tuning a downstream task. A weak score from that simple readout does not erase the model's richer frame-level representation. It says the cheap pooling method did not recover these categories.

The larger MERT model underperformed the smaller one. MERT 330M reached 0.200 while MERT 95M reached 0.216. Bigger cost twice the inference time and bought less category precision.

Every model produced a negative cosine silhouette score. The ten broad categories did not form clean islands in any embedding space.

Good. The numbers refused to flatter the taxonomy.

TEMPO AND KEY

Learned similarity did not replace deterministic analysis.

The nearest neighbors from every embedding lane still differed by roughly twenty-three to twenty-seven BPM after half-time and double-time correction. Correlation between embedding distance and tempo difference was weak across the board.

A model can hear timbre, production texture, instrumentation, or style while ignoring the pace required to mix two records. That is useful behavior. It becomes bad system design only when the interface pretends the embedding already handled tempo.

That still leaves forty-five percent outside the gate. Music Atlas should store the analyzer, value, confidence, and disagreement. It should show the user when two credible systems hear 85 and 170 rather than flattening both into one authoritative-looking number. The current archive already shows why musical key needs the same treatment. Source software disagrees, and the disagreement is material.

One clean number would be convenient. It would also be false.

THE ENGINEERING FRICTION

The card was not the hard part.

All heavyweight candidates fit the eight-gigabyte 2080 when they ran sequentially. OMAR-RQ produced the highest observed transient allocation at about 4.46 GiB during loading. Its steady run sat near 2.3 GiB. MusicFM and MuQ stayed near 1.4 GiB. MERT 330M used about 1.38 GiB. CLAP used 0.79 GiB, and MERT 95M used 0.51 GiB.

The constraints came from everything around the matrix multiplication.

01

The workstation began with an NVIDIA kernel and userspace mismatch. A reboot aligned the live and installed 595.84 driver stack.

02

Ollama was holding 5.5 GB of the card. The protocol unloaded its resident model before each heavy lane instead of tearing out a working local service.

03

MERT loaded two positional-convolution tensors incorrectly under PyTorch 2.6. The accepted Python 3.11, PyTorch 2.2, Transformers 4.38 environment loaded every checkpoint key through the legacy weight-normalization format.

04

MusicFM hid a small Conformer configuration dependency. MuQ-MuLan required separate local MuQ and XLM-RoBERTa encoders, then needed a direct strict state-dictionary load.

05

Essentia's TensorFlow runtime expected CUDA 11. I kept its frozen graphs on CPU and used CUDA 12 ONNX for generic Discogs.

06

The multi-target JSON advertised a 512-dimensional head that its graph did not expose. I tested the reachable 1,280-dimensional multi-trained backbone and labeled it honestly.

On the smoke clip, the GPU ONNX output matched the TensorFlow CPU output with minimum framewise cosine similarity of 0.99999988 and maximum absolute difference of 0.00000165. The Discogs track artifact host stalled, recovered before its conditional gate, and finished one hundred of one hundred.

None of this appears on a benchmark chart. All of it determines whether the system runs twice.

THE LICENSE BOUNDARY

A research winner can still be a production dead end.

The private test can use models that the public product cannot quietly inherit.

Permissive candidate

CLAP uses Apache 2.0. MusicFM lists MIT and Apache 2.0, with its upstream code and weight split still requiring confirmation.

Noncommercial weights

MERT and MuQ use CC BY-NC 4.0. OMAR-RQ weights use CC BY-NC-SA 4.0, while its code uses AGPL 3.0.

License or replace

MTG's Essentia weights use CC BY-NC-SA 4.0. Proprietary licensing is available from MTG.

The best research result is evidence for architecture and negotiation. It is not permission.

My first production spike would combine deterministic BPM and key analysis with Discogs ONNX embeddings for acoustic and style similarity. I would keep CLAP separate for text-to-audio queries and preserve the existing metadata graph for artists, versions, labels, release context, and acquisition leads. An embedding should find a relationship. It should not erase the relationship's source.

The other models remain research candidates until they survive listening and licensing. MuQ is especially interesting because it processed a clip in 0.073 seconds at the median and reached mean average precision of 0.251, stronger than its category precision rank suggests. MERT 95M remains a compact acoustic candidate. OMAR-RQ deserves a learned readout before any serious verdict.

THE NEXT GATE

The next test needs ears.

The automatic gate did its job. It removed models that failed to run, exposed compatibility traps, established real timing and memory use, and showed which representations recover the archive's broad organization. It also showed where the labels stop helping.

The next gate is blind human review. I will put the five nearest neighbors from all fifteen embedding lanes in front of the person who knows this archive, without showing the model name. Each result gets one judgment: useful, obvious, surprising but good, or wrong. Then I will take the smallest useful stack into a full-archive pilot.

I will not let a folder name decide what a DJ should hear next. That remains the work.
